# 课程新要求与现有平台偏差核对

核对日期：2026年10月13日。平台基线：`17f7519`，基金销售与模拟交易平台。

现有平台的基金销售方向、多银行卡账户模型及正常交易流程仍然适用。主要偏差是四项新增开发要求尚未完整覆盖，以及尚未按照老师模板交付正式需求规格说明书。其中，错误净值确认后的资产回滚与重新清算是最大的业务能力缺口，不能仅靠修改文案、重复执行任务或已有现金更正功能补齐。

## 一 核对依据与判定口径

老师材料：

- [系统开发的一些要求](系统开发的一些要求.docx)：四项具体开发要求，是本次业务与实现核对的直接依据。
- [需求规格说明书模板](模板-需求规格说明书.docx)：规定需求文档的组织方式和需说明的内容，其中的模块A、USB Key登录、机构代码等是填写示例。

平台依据：当前源码、数据库迁移、[设计草案](superpowers/specs/2026-10-04-fund-simulation-design.md)、[实现接口说明](implementation-contract.md)、[验收记录](acceptance.md)、[演示指南](demo-guide.md)及[运行说明](../README.md)。判定以实际代码为准，规划中列出但未落地的表或机制不算已实现。

“已有基础”表示相关能力可以复用，不表示已经达到老师完整要求。本次进行了材料与源码核对，没有执行真实交易、修改业务时钟或进行新的性能压测；性能部分据此区分确定的设计缺口与尚未测量的运行影响。

### 1 申请编号与确认编号

老师第（1）条要求的是两个业务编号，而不只是数据库记录有一个唯一主键。

当前实现：

- 普通申购、赎回使用`ORD-`加截断UUID，见[TradeService.java](../server/src/main/java/com/hengsheng/fund/TradeService.java)第50行。
- 认购使用`OF`加截断UUID，见[OfferingService.java](../server/src/main/java/com/hengsheng/fund/OfferingService.java)第47行。
- 定投执行生成普通申购，沿用上述订单编号；定投请求键不是独立申请编号，见[SipService.java](../server/src/main/java/com/hengsheng/fund/SipService.java)第75至76行。
- 转换记录使用自增ID，见[ConversionService.java](../server/src/main/java/com/hengsheng/fund/ConversionService.java)第65行。
- 普通确认只更新状态、净值、费用、份额和确认时间，没有产生独立确认编号，见TradeService第131行；认购和转换确认同样没有该编号。

[订单及事件表](../server/src/main/resources/db/migration/V1__core.sql)有`order_no`和自增事件ID，但后续确认时间迁移也没有增加老师要求的确认编号。订单号、数据库ID、请求幂等键、任务ID分别承担不同用途，不能互相替代这两个业务编号。

补齐方向：明确申请与确认各自的编号范围、工作日口径、每日序列和并发生成规则，并将编号保存到交易结果、查询页面及申请导出中。保留已有历史标识，不应为了新编号删除原有订单。

**老师原文有一处需统一：**文字写“序列不足5位左补0”，示例`20261010000001`却是8位日期加6位序列`000001`。当前材料还没有规定序列按日全局、按业务类型还是按TA划分，以及日期取受理日、归属交易日还是实际确认日。这些应先写清，不能自行把某一种解释当成老师已确认的要求。

### 2 清算与实时交易性能隔离

平台具有有利基础：自动任务在定时执行路径运行，确认与付款使用逐笔事务，一笔失败不必撤销整个批次的成功业务。这些有助于正确性和故障恢复，但不能单独证明实时交易性能不受清算影响。

具体存在共享锁竞争路径：

1. [FundService.market](../server/src/main/java/com/hengsheng/fund/FundService.java)第69行将整个行情生成方法放在事务中，第78行对开放产品集合执行`FOR UPDATE`。
2. 已有净值是否可以跳过，在获得产品锁以后才检查；产品锁可能持续到整次行情事务结束。
3. [TradeService.submit](../server/src/main/java/com/hengsheng/fund/TradeService.java)第26行的实时申购、赎回同样锁定产品行，因此同一产品的提交可能等待行情处理释放锁。
4. [application.yml](../server/src/main/resources/application.yml)只配置一套数据源，[Db.java](../server/src/main/java/com/hengsheng/fund/Db.java)统一使用同一JdbcTemplate。管理端手动清算也在HTTP请求内同步完成，见[CoreController](../server/src/main/java/com/hengsheng/fund/CoreController.java)第115至124行。

目前没有清算专用资源限额、执行并发控制、连接配额或清算与实时申赎同时运行的吞吐和延迟报告。现有并发测试主要验证不超扣等正确性，不等于性能压测。因此可以明确指出竞争风险，不能声称已经测出固定延迟或生产规模的性能瓶颈。

原先“不考虑企业级高并发、大数据量”的范围仍可用于确定课程验收规模，但老师现在明确要求考虑清算资源影响，不能再将此项排除。可先保留模块化单体，通过有上限的清算执行通道、短事务、收敛锁范围、分页处理与负载测试补齐；老师并未指定必须采用微服务、分库分表或消息队列。

### 3 错误净值确认后的资产回滚与重新清算

这项要求区别于初次清算、断点补跑和重复执行去重：**旧确认结果已经改变了资产，需要撤回其影响，再产生基于正确行情的新结果。**

当前实现明确阻止这一流程：

- [FundService.saveNav](../server/src/main/java/com/hengsheng/fund/FundService.java)第65行拒绝覆盖已经`published`或`used`的净值；首次发布即标记为已发布。
- 自动行情第80行对已有日期直接跳过，第85行使用`INSERT IGNORE`，不会更新错误历史净值。
- [TradeService.confirmOne](../server/src/main/java/com/hengsheng/fund/TradeService.java)第114行只处理`SUBMITTED`订单；已经确认、完成的订单再次执行会跳过。
- 已支付款项第134行也会跳过。当前没有撤回旧确认、相关持仓及钱包变动，再按新行情确认的服务或接口。

例如，净申购本金1000元按错误净值1.000000确认1000份；正确净值1.250000应对应800份。老师要求系统能撤回旧结果并重算，目前系统会拒绝修订已发布净值，重复点击确认也不会把1000份改成800份。涉及赎回时，还需要处理原来产生的应收、费用和现金变动。

以下已有功能都不能代替重新清算：

| 现有功能 | 能做什么 | 不能代替的原因 |
| --- | --- | --- |
| 普通撤单 | 截止前释放未确认申请的冻结资金或份额 | 已确认订单不允许撤销，见TradeService第63至64行 |
| 现金差额更正 | 关联已完成入账或提现，追加人工差额流水 | 不重算净值、费用、份额或清算依赖，见[CashCorrectionService](../server/src/main/java/com/hengsheng/fund/CashCorrectionService.java)第24至39行 |
| 重复执行任务 | 补跑尚未完成业务、防止重复入账 | 幂等机制主动跳过已完成结果，缺少新的清算修订轮次 |
| 整库备份恢复 | 把数据库恢复到备份状态 | 不能仅撤回某行情节点及下游结果，还可能覆盖无关后续申请，见[恢复脚本](../scripts/Restore-Local.ps1) |

后台当前有`MARKET / CONFIRM / PAY / SIP / MONEY / ALL`任务和结果历史，但`job_runs`主要保存日期、类型、计数和说明，并没有清算节点实例、行情修订版本、节点依赖或回滚状态。[CoreController](../server/src/main/java/com/hengsheng/fund/CoreController.java)第122至129行是固定顺序调用和事后汇总，不能视为可回滚的清算工作流。

现有产品规则版本、银行卡绑定版本也不等于行情修订或清算轮次。资金和份额流水及来源关联是后续实现的良好基础，但当前还没有利用它们完成自动冲正与重算。

补齐方向：保留原始行情和旧结果的审计记录，增加可区分的行情修订、清算轮次和节点结果，定位受影响确认及下游资产变化，完成受控冲正后再计算新结果。**只放开净值覆盖限制会使历史订单、持仓和账务互相矛盾，不是合格修复。**

需进一步界定的范围包括：仅当日还是允许跨日重清；是否涉及已支付款项；若后续赎回、转换、分红已经使用旧持仓，如何处理依赖；哪些账户或产品在重清期间需暂时限制操作。老师已经明确要求确认后可重清，不能将其缩减成只允许修改未确认行情。

### 4 当日交易申请文件导出

当前[CoreController.export](../server/src/main/java/com/hengsheng/fund/CoreController.java)第78至79行提供个人订单及资金流水CSV。它按当前登录用户查询全历史数据，没有按当日业务范围向登记过户系统提交申请文件的含义；转换记录也不在这个订单下载中。

实现采用`id > cursor`及每批200行查询，已有游标分批读取基础；但每批内容追加到`StringBuilder`，最后把完整字符串一次返回。查询分批不等于输出流式，文件变大后输出占用的内存仍随文件大小增长。

清算任务枚举没有导出节点，唯一业务调度为每五分钟扫描`ALL`，也没有老师描述的每工作日指定时间前导出任务。现有CSV表头来自数据库字段，不能直接当成已经约定的TA申请文件协议。

补齐方向：明确当日申请的日期口径、应包含的业务和客户范围、文件格式及截止时间；增加可记录结果的导出节点；复用游标查询改为边读边写文件，建立完整性检查和失败重导出的规则，再测量规定数据规模下能否按时完成。

老师材料尚未给出TA字段、编码、文件命名、传输方式或回执规范，不能擅自说必须接某家TA、采用SFTP或特定文件标准。课程可以采用明确的模拟文件协议，但必须能展示该节点及其性能设计。

## 四 不应误判成缺失功能的模板示例

- “模块或子系统A”“功能A1”是占位，需要替换成账户、交易、产品、清算等实际模块。
- USB Key证书、登录机构代码、8位输入框位于登录填写示例，不能据此认定必须采购USB Key、建立机构组织模型或把密码限制成8位。
- 模板让项目说明所用技术框架，没有指定必须换掉当前Vue、Spring Boot或MySQL。
- 模板列出容量、并发与时间指标，但没有给出具体TPS、在线人数或数据量；应明确课程适用指标，不能自行强加企业级数值。
- 镜像接管、多数据中心是容错等级示例，不代表本课程必须实现双活部署；需明确本项目选用的容错和恢复等级。
- 银行、TA和外部系统接口可以明确为教学模拟边界。两份材料没有要求真实资金交易或接入真实银行。
- 模板引用《产品性能指标说明》和《需求规格说明书-安全需求指南》，但本次两份文件未附这些文件内容，不能推断其中具体条款。
- 模板明确“不适用可写不适用，但不要删除标题”，正式需求书应保留其结构并说明适用性。

## 五 建议处理顺序与可验收结果

| 优先顺序 | 要做的事 | 建议验收场景 |
| --- | --- | --- |
| 1 | 明确重清范围、序列宽度、工作日及文件截止/格式口径；形成正式SRS基线 | 老师能逐项确认四条新增要求的含义，不把示例当成要求 |
| 2 | 实现行情修订、资产冲正及重新清算，并同步建立节点状态与依赖 | 用错误净值完成双卡申购/赎回确认，再修订行情重清；份额、资金、费用、待付款、流水和任务结果一致，重复执行不重复生效 |
| 3 | 补统一申请/确认业务编号和当日申请文件导出节点 | 同一工作日多笔、多账户及并发申请编号唯一；确认有独立编号；文件仅含约定日期范围内申请，失败重导规则明确 |
| 4 | 调整清算执行资源、事务锁范围和文件输出方式，补量化性能规格与测试 | 同时执行清算和实时申赎，测实时延迟与成功率；规定规模申请文件在截止前完成，监测内存和耗时 |
| 5 | 汇总需求规格、接口、流程图、测试追踪和演示材料 | 每条接受的需求有实现位置、验收方法及结果；未实现或不适用项有明确状态和范围 |
