# 清算与申请文件性能报告

## 清算与实时并行：测量范围

本报告只记录真实运行结果。完整验收采用需求规格中的 **20 会话、总 5 请求/秒、预热 2 分钟、测量 10 分钟、每组 3 次**。`quick` 是首轮短档基线：每组预热 10 秒、测量 60 秒、1 次；`smoke` 只有 2 秒预热和 5 秒测量，用来检查夹具。二者均不能代替完整验收。

脚本只从 `.runtime/local-env.json` 读取独立测试库连接配置，只允许名称精确匹配 `fund_sim_test` 或 `fund_sim_upgrade_test`，拒绝演示库 `fund_sim`。夹具在连接初始化前校验 URL，并将实际 `SELECT DATABASE()` 与从 URL 提取的允许库名核对。使用随机端口的真实 Spring Boot HTTP 服务、既有持久清算队列、实时池 8 和清算池 2；测量进程固定使用 `-Xms256m -Xmx512m -XX:+UnlockExperimentalVMOptions -XX:G1MaxNewSizePercent=10`，队列 1 个工作线程、4 个等待名额。这是与文件导出基线和部署启动统一的运行配置，JSON 记录实际 JVM 参数；运行时若未使用相同配置，本报告不能直接作为该配置的性能证明。申请文件目录使用 JUnit `@TempDir`，不启动或改动演示端口 8080/5173。

每一组重建相同规模的数据：1000 个夹具客户、每人 2 个模拟卡账户、20 只基金、10000 笔历史申购、2000 笔待确认申购。历史申请直接构建为升级前可读记录，配套真实结构的钱包、预约/消费现金流水、持仓和份额/成本流水；历史数据构建时间不计入清算耗时。待确认订单只预建受理及资金预约状态，计时内由原生产确认服务生成实际确认、持仓和消费流水，不修改服务行为。

清算入口本身是全平台扫描，因此使用尚未使用的随机早期工作日，并先断言该日期前没有其他测试的待确认订单或转换。业务时钟保持测试库当前值。`finally` 只清理本次随机用户、TA、来源订单、任务和新插入日期；外键保持启用，其他用户及演示库数据不清理。确认编号使用当前业务日；来源编号登记精准清理后，该日全平台序列仍保留增长，不能为消除空洞而重置共享序列。

20 个独立登录会话以每 200ms 计划一次请求，交替执行 `/portfolio`、钱包查询、真实充值、真实提现及同一提现请求键重试。负载不会等上一请求完成后再降速；证据包含每一请求的实际延迟、含客户端调度等待的延迟、HTTP 状态、会话号以及是否与入队到任务终态的区间重叠。该负载验证账户查询和现金实时写入，尚不代表同时申购/赎回受理或重清账户门禁的性能验收。

比较三组：无批次；真实 2000 笔确认并行；真实 10000 笔历史申请快照构建和文件写入并行。每组结束检查钱包可用/冻结金额与全部流水、批次可用/冻结份额及成本与全部份额流水。确认组另检查 2000 笔全部完成、2000 份确认和 2000 个来源批次，原请求键返回原任务，新请求键复跑无新增确认和份额。导出组核验 10000 数据行及实际文件 SHA-256。

首个命令只验证建数和账务后精准清理，不留下公共数据集。每个测量档输出 `.runtime/clearing-performance-<档名>.log` 和 `.runtime/clearing-performance-<档名>.json`；JSON 包括全部逐请求原始样本、实际请求速率、P95、错误数量、并行窗口样本数量、批次耗时、5ms 间隔的 JVM 堆采样和实际连接占用峰值。只有成功 HTTP 请求参与 P95，失败请求单独列数，不当作成功样本。整段 P95 与批次活动窗口 P95 分别记录和比较；文件生成窗口较短时，须结合重叠样本数评估，不能以任务结束后的大量请求稀释活动窗口影响。

测试绿色证明账务、幂等、真实并行及文件校验通过。响应阈值以 JSON 的 `absoluteLatencyGatePassed`、`parallelLatencyGatePassed` 和 `parallelWindowLatencyGatePassed` 单独判定；这些是实测判定字段，不是测试断言，不能把 Maven 绿色直接写成所有性能门槛通过。批次耗时门槛也须以实际数字单独核对。

堆峰值是整个实时加批次进程的观测值，包含实时工作负载与尚未回收对象；不能单凭本组堆增量宣称“文件批次增量堆 ≤64MiB”。独立文件分段堆测量及 10 万行专项由文件导出性能章节另行记录。
